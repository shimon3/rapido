# Revue S2/S3 — 14 octobre 2026

Base inspectée : 387ac76bd326caf69de97093cd4b537154c9159a (PR #21).
Cette revue de code ne constitue pas une validation dans Chrome/Edge/Firefox
réels ni un test de compromission d'un poste utilisateur.

## Résultats et limites confirmés dans le code

| Chemin | Protection présente | Limite restante |
| --- | --- | --- |
| windows_peer.py, verified_process | PID du noyau, SID, chemin complet, heure de création, handle de processus conservé | Aucun contrôle du contenu ou du signataire du fichier |
| native_pipe.py | Vérification du pair avant le payload, DACL, première instance, refus réseau distant | Le nom et le SID autorisés ne prouvent pas l'intégrité du code chargé |
| native_launcher.py | Chaîne de parents Windows réelle, SID, origine exacte et chemins de navigateurs attendus | Un navigateur/host autorisé modifié ou injecté n'est pas détecté |
| native_registration.py et packaging/rapido.iss | Identités d'extension explicites, protection des registrations d'une autre installation | Installation LocalAppData et HKCU ne sont pas une ancre inaccessible au même compte |
| engine.py | DPAPI pour l'historique Windows, absence de repli en clair | DPAPI protège par compte ; ce n'est pas une isolation entre programmes du même compte |

Un programme dont le contenu a été remplacé au chemin exact autorisé peut
satisfaire le test SID/chemin. C'est une conséquence de la politique actuelle,
constatée par relecture ; aucun remplacement des exécutables de l'utilisateur
n'a été exécuté. De plus, une registration HKCU modifiée peut sélectionner un
autre host avant que Rapido soit consulté : une signature vérifiée seulement
par le code de l'ancien host ne suffit pas à garantir le nouveau host lancé
par le navigateur. L'ID allowed_origins autorise l'extension appelante ;
ce n'est pas une attestation de l'intégrité du host.

Ne pas déclarer ces attaques corrigées par une empreinte enregistrée à côté de
l'exécutable, un secret DPAPI lisible par le même compte, ou une auto-vérification
que le programme remplacé pourrait omettre.

## Voie de durcissement à préparer

1. Définir explicitement la frontière : autre compte, processus ordinaire du
   même compte, ou compromission des programmes/fichiers du même compte.
2. Pour des fichiers fiables : vérifier signature Authenticode ET identité
   attendue du signataire, sur un handle de fichier conservé, avec tests de
   signature absente/invalide/autre éditeur et de remplacement pendant le contrôle.
   Accepter toute signature Windows valide ne suffit pas.
3. Pour empêcher l'exécution d'un host modifié avant réception des données :
   protéger les binaires et la registration au niveau système et appliquer une
   politique de contrôle d'applications. L'installation machine et la politique
   nécessitent un déploiement administré ; rien n'a été modifié sur ce poste.
4. Vérifier la disponibilité et la gestion d'une identité de signature.
   Aucun certificat/secret de signature n'a été supposé disponible ou créé.
5. Tester les attaques et les mises à jour/retours de version sur Windows réel.

Cette branche ne prétend pas implémenter cette ancre système. Une signature seule
sans politique d'exécution et sans protection du lancement du host ne clôture pas
le scénario complet de compromission du même compte.

## Correction S3 des contextes privés

La capture automatique et le menu contextuel refusent les stores Firefox autres
que firefox-default, les stores inconnus et les contextes Firefox sans store
identifiable. La vérification des cookies ordinaires Firefox précise
storeId=firefox-default. Aucun cookie ni URL de conteneur n'est envoyé au pont.
La collecte de médias privée est également refusée avant stockage en session.
Chrome/Edge ordinaires sans cookieStoreId conservent le chemin existant.
Les appels vidéo issus d'un onglet privé/conteneur sont refusés avant lecture
des candidats ; la capture vidéo reste désactivée pour les autres onglets.

Tests Node sur le vrai background.js avec APIs simulées : conteneur, store privé,
store inconnu/absent, clic droit, médias privés, cookies par store et régressions
du chemin ordinaire. Ces tests ne remplacent pas les essais des navigateurs réels.
